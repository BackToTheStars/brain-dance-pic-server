# brain-dance-pic-server

Сервис хранит изображения, аудио, видео и pdf в MongoDB GridFS.

## Пересборка образа: yt-dlp и ffmpeg

В образе стоят `yt-dlp` и `ffmpeg` (перенос видео с YouTube, `POST /youtube/probe` и
`POST /youtube/download`). Версия зафиксирована в `Dockerfile` — `ARG YTDLP_VERSION`
и `ARG YTDLP_SHA256`.

**Образ нужно периодически пересобирать с новой версией.** YouTube регулярно ломает
извлечение, и зафиксированный yt-dlp в какой-то момент просто перестаёт скачивать —
починка выглядит как обновление этих двух `ARG`:

```
YTDLP_VERSION — тег релиза https://github.com/yt-dlp/yt-dlp/releases
YTDLP_SHA256  — строка для файла `yt-dlp` из SHA2-256SUMS того же релиза
```

Сборка сама проверит контрольную сумму и выполнит `yt-dlp --version`, поэтому
неверная пара версия/сумма роняет билд, а не прод.

`ffmpeg` нужен для склейки. Progressive-форматов, где видео и звук лежат в одном
файле, у YouTube больше нет, поэтому дорожки качаются по отдельности и склеиваются
в mp4; контейнеры совместимы, так что это remux (`-c copy`), без перекодирования.
Версия ffmpeg не пинуется — берётся из репозитория Alpine.

Для локальной отладки (`npm run dev:media` идёт на хосте, а не в контейнере) нужны
`yt-dlp` и `ffmpeg` на PATH машины; путь к yt-dlp можно задать переменной
`YTDLP_BIN`. Без ffmpeg скачивание пары дорожек не выполнится — probe при этом
работает как обычно.

Тот же пакет `ffmpeg` даёт и `ffprobe` (в образе — `/usr/bin/ffmpeg` и `/usr/bin/ffprobe`); оба
нужны кадру из видео (ниже). Пути — переменные `FFMPEG_BIN` и `FFPROBE_BIN`, по умолчанию
имена `ffmpeg` и `ffprobe` с PATH.

## Токен для защищённых ручек

Токен требуют `upload`, `download-and-save`, `/stats`, `/limits`, `/files`, `/youtube/*`,
`/videos/:filename/frame` и — с волны 6 — `DELETE /<тип>/:id`. Отдача (`GET /<тип>/:filename`)
намеренно открыта: файл читает браузер по прямой ссылке.

В токене лежит операция, и middleware сверяет её с ручкой: без заголовка — 401, с битым
токеном — 403, с токеном чужой операции — 400 `Invalid operation`. Операции:
`upload`, `download_and_save`, `delete`, `stats`, `limits`, `list`, `youtube`, `frame`,
`frame_save`, `files_maintenance`.

**Служебная метка.** Токен загрузки игроку подписывает тот же server тем же секретом, поэтому
подпись не отличает игрока от сервера. Все операции, кроме `upload`, принимаются только с
`scope: 'service'` в полезной нагрузке — её ставит server в своих служебных токенах; без
метки — **403** `{ "message": "Service token required" }` (проверка идёт после сверки
операции, так что токен `upload` на `/files` по-прежнему получает 400). Новая операция
считается служебной, пока её не внесут в `CLIENT_OPERATIONS` (`config/media.js`).

**Игра файла.** Если в токене есть `gameId`, новый файл получает в `metadata` пару
`gameId` (строкой) и `gameHash` (строка `hash` из токена, если она непуста) — и в описи, и
в GridFS, на всех путях записи (`upload`, `download-and-save`, `youtube/download`, сохранение
кадра). Ключи `gameId` / `gameHash` из тела запроса отбрасываются всегда, как и
`originalnameLatin1` (его ставит только `scripts/names.js`). Нет `gameId` в токене — нет и
ключей. Больше `hash` ни с чем не сверяется. Старым файлам пару ставит служебный проход
`POST /files/game-backfill` (ниже) с меткой `gameBackfill: true`; эта метка и мёртвые ключи
`uploader` / `downloader` из тела тоже отбрасываются.

Команды для выпуска токена в репозитории нет: `npm run token` звал `scripts/tokens.js`,
которого не стало ещё в `ec448c7`; мёртвая строка позже убрана из `package.json`. Токен
подписывается однострочником — из каталога `media`, операция подставляется вторым
аргументом, остальное полезной нагрузки — четвёртым (здесь служебный `delete`, срок жизни
5 минут):

```
node -e "require('dotenv').config();const {getToken}=require('./modules/auth/lib/token');console.log(getToken(process.env.JWT_SECRET_STATIC,'delete',Date.now()+300000,{scope:'service'}))"
```

Дальше — обычным curl:

```
curl -X DELETE -H "Authorization: Bearer <токен>" http://localhost:3011/images/<id>
```

## Список файлов: `GET /files`

Ручка админской таблицы. К типу медиа не привязана — тип здесь фильтр,
а не адрес, — поэтому живёт рядом с `/stats`, а не внутри `/<тип>`. Защита та же, что у
`/stats`, операция в токене — `list`; серверный прокси (следующая волна) подписывает его
так же, как для `/admin/media/stats`.

| параметр | значения | по умолчанию |
|---|---|---|
| `type` | `audios`, `videos`, `images`, `pdfs`; можно списком через запятую | все |
| `name` | подстрока: `filename`, `metadata.originalname`, `metadata.originalUrl`, `metadata.title`; регистр не важен, спецсимволы регэкспа экранируются | — |
| `game` | адрес игры, точное совпадение с `metadata.gameHash`; одно значение из латиницы, цифр, `-` и `_`, до 64 символов | — |
| `minSize`, `maxSize` | байты, по реальному размеру файла в GridFS | — |
| `from`, `to` | дата: ISO-строка или миллисекунды; по `uploadDate` записи | — |
| `sort` | `uploadDate`, `filename`, `size`, `storedAt`, `accessCount`, `lastAccessAt` | `uploadDate` |
| `order` | `asc`, `desc` | `desc` |
| `page`, `limit` | целые: `page` до 10000, `limit` до 200 | `1`, `50` |

Ответ — `{ items, total, page, limit }`. В элементе есть и поля записи `Media`
(`filename`, `contentType`, `uploadDate`, `originalname`/`originalUrl`/`title` и
`gameHash`/`gameId` из метаданных — у файла без игры `null`, `accessCount`,
`lastAccessAt`, `src`), и то, что видно только сверкой с GridFS: `size`, `storedAt`
(оба — от последней версии, той, что отдаётся), `fileCount`, `missing` (запись есть,
файла нет) и `duplicate` (одноимённых файлов больше одного). Ошибки разбора query — 400,
все сразу одной строкой.

Пагинация серверная и обязательная. Типы — разные коллекции и разные бакеты, поэтому у
каждого берётся начало выдачи длиной `page × limit`, результаты сливаются в общий
порядок и режется страница; порядок устойчив — второй ключ сортировки `_id`.

Сверка с GridFS идёт по странице: записи отбираются и сортируются в своей коллекции, и
только потом одним запросом добираются файлы по именам этой страницы. Исключение —
фильтр по размеру и сортировка по `size`/`storedAt`: там соединение неизбежно раньше
отбора страницы, и делается оно одним `$lookup` на тип по всем записям, прошедшим
фильтр. Записи без файла в такую выдачу не попадают: размера у них нет.

```
curl -H "Authorization: Bearer <токен операции list>" \
  "http://localhost:3011/files?type=images&name=logo&sort=size&order=desc&limit=20"
```

## Служебные проходы по metadata: `POST /files/dead-keys`, `POST /files/game-backfill`

Операция `files_maintenance`, служебная. Тело — JSON; ошибка тела — 400 одной строкой со всеми
причинами. Смотрят оба места: запись описи `<тип>` и все версии имени в `<тип>.files`.
Списки в ответах обрезаны до `listLimit` (100), счётчики — полные.

**Мёртвые ключи** `uploader` и `downloader` писались первыми версиями сервиса, всегда `null`, и
никто их не читает; новые файлы их больше не получают.

- `{ "mode": "report" | "apply", "types"?: ["images", …] | "images,pdfs" }` (по умолчанию все типы).
- Ответ: `{ mode, keys, totals, byType: [ … ], listLimit }`; в `byType[i]` — `records` и `files`
  (`total` и по каждому ключу `{ null, notNull }`), `notNull` (документы с непустым значением: место,
  `_id`, имя, ключ, значение до 100 символов), `recordsWithoutFile` и `filesWithoutRecord`
  (`{ count, names }`). Счётчики — до снятия.
- `apply` снимает ключ **только со значением `null`** в обоих местах и возвращает `removed`
  (`{ records: { uploader, downloader }, files: … }` по типу и в `totals`); непустые не трогает;
  повтор снимает 0. Отката нет: `null` ничего не несёт.

**Игра файла** — пара `gameId` / `gameHash` старым файлам по ссылкам, которые собирает server.

- `report` и `apply`: `{ "mode", "gameId"?, "items": [{ "type", "filename", "gameId", "gameHash" }] }`,
  не больше 10000 элементов. `type` — тип media, `filename` — системное имя (1–255 символов, без `/`,
  `\`, управляющих), `gameId` — 24 hex в нижнем регистре, `gameHash` — как фильтр `?game=`. `gameId`
  запроса (необязательный) — предохранитель: элемент другой игры становится `invalid`.
- Вердикт файла: `missing` (нет ни записи, ни файла), `recordOnly`, `fileOnly`, `badMetadata`
  (`metadata` не объект), `conflict` (где-то стоит другая или неполная пара — список `existing`),
  `same` (везде та же пара), `pending` (к записи). Негодный элемент — `invalid` с причинами; один
  файл с разными парами в одном запросе — `ambiguous`; одинаковые элементы схлопываются (`repeated`).
- `apply` пишет `gameId`, `gameHash` и `gameBackfill: true` только у `pending` и только туда, где нет
  ни `gameId`, ни `gameHash` (опись и все версии GridFS) — условным `updateMany`; уже стоящая пара
  не перезаписывается никогда; повтор пишет 0.
- Ответ: `{ mode, gameId, items: { received, repeated, invalid, ambiguous, files }, counts,
  toWrite: { records, files }, written (только apply), byType, marked, lists, listLimit }`; `marked` —
  сколько документов с меткой (в рамках `gameId` запроса) после операции.
- `revert`: `{ "mode": "revert", "gameId"?, "types"? }` — без `items`; снимает `gameId`, `gameHash`
  и метку **только у документов с `gameBackfill: true`** (с `gameId` — только этой игры). Ответ:
  `{ mode, gameId, types, reverted: { records, files, byType }, marked }`.

## Учёт обращений

`GET /<тип>/:filename` считает обращения: `accessCount` и `lastAccessAt` в записи `Media`.
Считается только начало просмотра — запрос без `Range` либо с `Range`,
начинающимся с нуля, — и не чаще раза в `ACCESS_COUNT_WINDOW` (`config/media.js`, сейчас
3 минуты) на файл, одним условным `updateOne`. Иначе один просмотр видео дал бы десятки
записей, и цифра означала бы рваность сети, а не спрос.

Отдача остаётся без токена, и накрутить счётчик может кто угодно — это принято осознанно:
обращение к файлу и есть признак востребованности. У записей, сделанных до этой волны,
полей нет; первое же обращение их заводит, а в выдаче `/files` они читаются как `0` и
«не обращались».

`Range` разбирается по RFC 9110 (`modules/media/services/range.js`): `bytes=-N` — последние N байт
(N не меньше размера — весь файл, 206), конец за размером усекается, начало не меньше размера —
416 с `Content-Range: bytes */<размер>`; негодная запись и несколько диапазонов игнорируются —
200 и весь файл. Суффиксный диапазон считается началом просмотра, только если покрыл файл с нуля.

Не считается чтение самим сервисом: ffmpeg кадра из видео шлёт заголовок
`x-media-internal-read` со случайным значением, которое знает только процесс media.

Брошенный клиентом ответ (перемотка видео, отменённый `Range`) закрывает курсор GridFS: без
этого каждый обрыв оставлял в памяти около 16 МБ.

## Отчёт по лимитам: `GET /limits`

Операция `limits`, служебная. Только чтение: все потолки загрузки по цепочке и откуда взято
каждое значение (`source`: `code`, `env`, `cgroup`, `os`, `mongo`, `unknown`).

```
{
  "nginx":       { "value": "350m", "bytes": 367001600, "unlimited": false, "source": "env", "env": "NGINX_CLIENT_MAX_BODY_SIZE" },
  "upload":      { "audios": { "bytes": 367001600, "source": "code" }, …, "pdfs": { "bytes": 52428800, "source": "code" } },
  "requestBody": { "bytes": 367001600, "source": "code" },
  "memory": {
    "limit": { "bytes": null, "unlimited": true, "source": "cgroup", "file": "/sys/fs/cgroup/memory.max" },
    "host": { "bytes": 8160000000, "source": "os" },
    "uploadFactor": 2,
    "hint": "Загрузка держит файл в памяти целиком, на пике — около двух его размеров: …"
  },
  "storage": { "free": 980347039744, "total": 1081101176832, "source": "mongo" }
}
```

- **nginx** — `client_max_body_size` vhost'а media, строкой как в конфиге nginx, из переменной
  `NGINX_CLIENT_MAX_BODY_SIZE`: media сама его не видит. Не задана — `source: "unknown"`, `bytes: null`,
  числа не подставляется. Строка не по синтаксису nginx — `value` как есть, `bytes: null`; `0` —
  `unlimited: true`.
- **upload** — `getUploadLimit` по типам, та же функция, что у multer, download-and-save и youtube.
- **requestBody** — лимит `express.json` / `express.urlencoded` (`REQUEST_BODY_LIMIT`); multipart-загрузку
  ограничивает `upload`.
- **memory.limit** — cgroup v2 `memory.max` (`max` — без ограничения), иначе v1
  `memory.limit_in_bytes` (число около 2^63 — без ограничения); файлов нет (Windows, хост без
  cgroup) — `unknown`. `memory.host` — `os.totalmem()`, в контейнере это память хоста.
- **storage** — свободное место на диске mongo, те же данные, что `fs` в `/stats` (и тот же кэш).

## Кадр из видео: `/videos/:filename/frame`

Только у `videos`. Видео ищется по системному имени (`uuid.ext`) в описи и GridFS.

- `GET /videos/:filename/frame?t=<секунды>`, операция `frame` — предпросмотр, ничего не сохраняет.
  Ответ: `{ t, duration, mimetype: "image/jpeg", size, dataUrl: "data:image/jpeg;base64,…" }`.
- `POST /videos/:filename/frame`, тело `{ t, metadata? }`, операция `frame_save` — кадр снимается
  заново и ложится в `images` новым файлом, прежние не трогаются. Ответ как у загрузки:
  `{ src, item: { _id, filename } }`. `metadata` картинки: поля тела (без `gameId`, `gameHash`,
  `originalnameLatin1`), `mimetype`, `originalname` = `<имя видео без расширения>-frame-<t>.jpg`
  (имя видео — `originalname`, иначе `title`, иначе системное имя), `sourceVideo` — системное имя
  видео, `frameTime` — `t`, и игра из токена.

`t` — неотрицательное число секунд (в строке — только цифры и точка), не больше длительности
видео; точность — миллисекунды. Кадр — JPEG, не больше 1280 точек по большей стороне. Если между
последним кадром и концом дорожки кадра в момент `t` нет, берётся последний кадр перед `t`.

| ответ | когда |
|---|---|
| 400 `t — число секунд от 0 до длительности видео.` | `t` нет, не число, отрицательное, передан дважды |
| 400 `t больше длительности видео (… с).` | `t` за длительностью |
| 400 `В файле нет видеодорожки.` / `Файл не читается как видео.` / `В момент … с в видео нет кадра.` | файл не видео или кадра нет |
| 404 `Video not found.` | нет записи или файла в `videos` |
| 429 `Уже снимаются другие кадры, …` | уже идут два кадра |
| 504 `Кадр не снят за 60 с.` | таймаут `FFMPEG_FRAME_TIMEOUT` на ffprobe или ffmpeg |
| 502 | ffmpeg / ffprobe не найден или ответил не по контракту |

Устройство: ffprobe и ffmpeg читают видео по HTTP самого сервиса (`http://127.0.0.1:<MEDIA_PORT>`)
диапазонами, поэтому память и диск не зависят от размера видео; кадр пишется файлом во временный
каталог (корень `YOUTUBE_TMP_DIR`), не в stdout. ffmpeg принимает только протокол http и
контейнеры mp4/mov, webm/mkv, ogg, avi — загруженный «видеофайл» с плейлистом внутри не
откроет другие файлы. Процесс снимается по таймауту и по закрытию соединения.

## Одна версия файла и занятое имя

GridFS разрешает несколько файлов с одним `filename`. Актуальная версия — последняя
(`uploadDate`, при равенстве — `_id`): от неё отдача берёт и `Content-Length` /
`Content-Range`, и сами байты (поток открывается по `_id` найденной версии), от неё же
`size` в `/files`. `DELETE /<тип>/:id` удаляет все версии имени вместе с записью.

Новый файл под уже занятым именем не записывается (`modules/media/services/store.js`,
общий для всех путей записи): имя проверяется в описи и в GridFS до записи байт, а гонку
двух записей ловит уникальный индекс описи `filename_1` — проигравшая запись убирает
свой файл из GridFS. Отказ — 409 `File name is already taken.`; через API до него не
дойти, имена — uuid. На базе, где одноимённые записи описи уже есть, индекс не строится:
сервис стартует и пишет в лог строку `[indexes] <тип>: НЕ ПОСТРОЕНЫ ИНДЕКСЫ filename_1 — …`,
проверка перед записью при этом работает.

## Осиротевшие файлы и одноимённые записи: `scripts/orphans.js`

Сирота — файл в GridFS, на который нет записи `Media`: через API он недоступен (и отдача,
и удаление сначала ищут запись и отвечают 404), но место занимает и виден в `byType`
из `/stats`. Скрипт ходит в ту же базу, что и сервис (`MONGO_URL` из `.env`; для другой
базы — переменной окружения перед командой).

```
node scripts/orphans.js                       отчёт по всем типам, ничего не меняет
node scripts/orphans.js --type=images         отчёт по одному типу
node scripts/orphans.js --delete --all        снести всех найденных сирот
node scripts/orphans.js --delete --type=videos
node scripts/orphans.js --delete --id=<id>    снести конкретные файлы
```

Без `--delete` скрипт только показывает. Голый `--delete` без цели (`--all`, `--type`
или `--id`) — ошибка, чтобы «снеси, что найдёшь» нельзя было запустить случайно.

Тем же проходом отчёт показывает одноимённые версии в GridFS — у имён с записью `Media`
(отдаваемая помечена `← отдаётся`) и без неё (эти же файлы есть и в списке сирот) — и
одноимённые записи описи, с размерами и датами, и итоговую строку «Итого одноимённых».
Одноимённые версии и записи скрипт не удаляет никогда.

В контейнере — `docker compose exec media-app node scripts/orphans.js`.

## Испорченные имена: `scripts/names.js`

До правки приёма multer читал имя файла из multipart как latin1, и кириллица (и любой
не-ASCII) ложилась в `metadata.originalname` строкой вида `Ð¢Ð°Ð±Ð»Ð¸ÑÐ°.pdf`. Имя лежит в
двух местах — в записи описи и в `metadata` документа `<тип>.files`; скрипт смотрит оба.

```
node scripts/names.js                 отчёт: восстанавливается, не восстанавливается, примеры
node scripts/names.js --type=pdfs     отчёт по одному типу
node scripts/names.js --apply         исправить восстановимые
node scripts/names.js --revert        вернуть прежние значения
```

«Восстанавливается» — все символы не выше U+00FF, есть хотя бы один выше U+007F, и
перекодировка latin1 → UTF-8 проходит без символа замены (законное `café.pdf` сюда не
попадает). «Не восстанавливается» — перекодировка не удалась, но в имени есть управляющий
символ C1 или пара «ведущий байт + байт продолжения»; такие не трогаются и перечисляются.
`--apply` кладёт прежнее значение в `metadata.originalnameLatin1` и правит только
документы без этого поля, поэтому повтор ничего не меняет. `--revert` возвращает имя из
этого поля и снимает его — только если текущее имя совпадает с починкой сохранённого.

В контейнере — `docker compose exec media-app node scripts/names.js`.
